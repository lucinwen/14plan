## 综合题
**题目：**上层发出“去B房间”目标，机器人在狭窄门口停下。Nav2的Planner、Controller和TF各自干了什么？

**参考推理：**Planner利用地图/代价图等规划路线；Controller基于状态反馈执行路径跟踪；TF提供随时间变化的参考坐标变换。门口停止可能是机器人footprint加障碍膨胀后不可通过、定位/时间戳错误、动态障碍或控制约束。应记录具体反馈，不把“看见门”当能通行。

**检查证据等级：**若本日只做纸面推导，不能宣称本地实际运行或仿真执行完成。每条结论标“理论/合成数据/开源示例/本人实测/历史亲自工作”。

## 关键问答（脱稿再说一遍）
### Q1：Topic与Action差别？
Topic更适合连续数据流；Action适合可取消、带反馈和结果的长时任务。

**追问：**换机器人尺寸、动作限制或初始场景后，上述判断需要哪些新增观测与实验？

### Q2：TF和URDF区别？
TF是参考坐标系间动态/静态关系；URDF描述机器人link、joint与几何惯量等结构配置。

**追问：**换机器人尺寸、动作限制或初始场景后，上述判断需要哪些新增观测与实验？

### Q3：Planner与Controller区别？
Planner产生路径/轨迹目标，Controller根据当前状态持续计算控制指令执行。

## 补充参考解｜ROS2导航闭环

~~~text
Task Planner → Nav2 Action Server(goal in map frame)
     → Global Planner(path) → Local Controller(cmd_vel)
     → Robot + Sensors → odom/TF/costmap → feedback/result → Task Planner
~~~

`map`是全局地图参考帧，`odom`可连续跟踪短时运动但会漂移，`base_link`为机器人本体坐标。系统必须提供有效时间戳的变换；TF树不自动证明定位准确。

**题一：门窄**。有声明拓扑路径，但底盘+安全余量大于门净宽；全局/局部规划可拒绝或控制受阻。应检查footprint/costmap和门状态，而不是只重新发送goal。

**题二：门锁**。物理地图可能没有动态“锁”状态；机器人没有开锁技能时，高层任务不可行，不是ROS2话题编排的故障。

**概念纠错**：Action提供goal、反馈、取消、结果机制，不能保证执行成功；URDF提供结构/关节而非实时世界位姿；Nav2 Planner做路径、Controller跟踪执行命令，二者角色不同。回答必须能在自己图上指出哪一个模块检测到失败、哪一个模块拥有修复权。
