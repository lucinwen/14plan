# Day 13｜2026-11-01｜Belean 比邻：双人空间共在、坐标一致性与授权触碰

> **2026-11-01 / Day13 / P2 / 10小时有效学习（休息另计）**  
> **核心问题**：两个人的媒体已连接，怎样确保双方在**同一空间版本**中看到正确位置、知道彼此的授权状态，并在跟踪/网络出错时安全退出？

## 今天只需理解这五层
1. **用户与场景**：主场可能由A或B提供，创建者身份不等于空间所有者。
2. **共用世界**：空间提案、双方同意、版本 revision、双方分别 ready；GLB/实测尺寸属于已具备的软件入口，真实3DGS房间尚需研发。
3. **空间与身体**：头/双手6DoF、WebXR本地参考空间、手动地面对齐、变换方向、跟踪新鲜度。
4. **通信与体验**：WebRTC人物音视频/独立屏幕分享；WebSocket应用状态、姿态和授权；可选HRTF；服务与真实媒体体验需分开验收。
5. **可撤回互动**：触碰双向许可和接收方当次同意，本地停止优先；当前默认视觉/可选Gamepad，不等于实体触觉设备输出。

**不要强行把 Belean 说成机器人远程操作系统**。它与具身智能的交集在空间与身体动作表示、交互状态、安全与可验证体验。

## 今日核心练习
**假设**两人在共享空间revision7，B提出另一房间并得到A接受，服务端进入revision8；A加载确认但B仍未确认，rev7的手部位姿此时迟到。你要写：A和B分别能看到什么、是否能允许触碰、旧位姿如何处理、为何WebRTC还连着也不能当作一切就绪。

进一步设计一条“真实房间高斯外观正确，但桌面的触碰代理丢失”的安全反例。该案例是教学推演，**不是 Belean 已通过两地真实房间/实体触觉的证明**。

## 技术面试追问
1. 谁创建房间，谁提供主场，谁接受提案，谁确认加载？为什么是不同字段？
2. WebRTC已有视频为什么WebXR远端人仍可能站错位置？
3. 换空间后怎样拒绝旧位姿、旧触碰请求和旧授权？
4. 3DGS外观好为什么不能推断真实房间安全可走/可触？
5. 什么时候该降级为普通通话或停止输出？
